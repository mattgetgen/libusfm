# libusfm 0.1.1

A speed-only release: the scanner finds text and attribute boundaries
64 bytes at a time with SIMD. The public API, the AST and every parse
result are unchanged.

## What changed

- A new internal block classifier, with SSE2, AVX2, AVX-512BW, NEON and
  wasm simd128 versions. The version is chosen at compile time (see the
  SIMD comment in `usfm.h`); there is no runtime CPU detection. A plain
  x86-64 build gets SSE2; build with `-mavx2` or `-march=native` for AVX2.
- The scanner caches the masks of its current 64-byte block, so one
  classification serves every token in that block.
- A new configuration macro, `USFM_SIMD_NONE`, forces the v0.1 byte loops.
- Nothing is read past the end of the input on any path. A partial last
  block is classified from a zero-padded copy.

## Verification

- The block scanner and the v0.1 byte-loop scanner are compared token by
  token: in the unit tests (crafted inputs around every 64-byte boundary,
  every input length up to 512 bytes, 20,000 random inputs), over every
  bundled corpus, and on every fuzz input. Every SIMD classifier is
  compared against a scalar reference, including on every 64-byte block
  of every corpus.
- The bundled corpora are WEB-STRONGS (the World English Bible with a
  Strong's tag on every word, the only corpus before this release), WEB
  (the same text untagged), HBO-WLC (Hebrew), CMN-CUV (Chinese), ARB-VD
  (Arabic) and GRC-BYZ (Greek); all of them are run on every SIMD path
  and each gives an identical AST checksum on scalar, SSE2 and AVX2
  (native), NEON (`qemu-aarch64`) and wasm simd128 (`zig cc`, Node
  WASI). See `tests/corpus/README.md`.
- AVX-512BW compiles cleanly but has not been run yet. It needs Intel SDE
  (`USFM_SDE=/path/to/sde64 ./build.sh test-avx512`) or AVX-512 hardware.
- Six local Paratext projects (448 books) also gave identical tokens on
  SSE2 and AVX2.
- A 30-minute libFuzzer run on the AVX2 build found nothing: 7.57M inputs,
  each also checked by the two-scanner comparison, with no crashes, leaks,
  timeouts or scanner differences.

## Performance

Two changes make 0.1.1 faster than 0.1.0:

- **SIMD scanning** of text and attribute runs (SSE2, AVX2).
- **O(1) text-flag upkeep when trimming.** 0.1.0 rescanned a whole text
  node after trimming its trailing newline, to recompute the CR/LF/TAB
  flag. That was a third of all parse instructions on WEB. It now uses
  the first CR/LF/TAB offset the scanner already saw. This helps every
  build, including scalar.

Whole-corpus parse (parse + free), fastest of 27 passes, clang -O3
-march=native, Intel i7-1355U with the power profile set to
"performance", current corpus snapshots, measured 2026-11-17/18.
"0.1.0" is the 0.1.0 header. The 0.1.1 columns differ only in which SIMD
path is compiled in: scalar is `USFM_SIMD_NONE`.

## Compared with other USFM parsers

Each parser parsed every corpus with its own benchmark harness on the same
machine on 2026-11-17/18, power profile "performance", pinned with
`taskset -c 0-3`. Figures are the fastest whole-corpus pass in MiB/s.
Passes: libusfm 27; usfm_tools 5 after 1 warm-up; usfm3, tree-sitter
and the `usfm` crate 3 after 1 warm-up; ParatextData 20 after 3 warm-ups;
usfm-grammar 10 after 3 warm-ups; usfmtc 2.

- **ParatextData needs a long warm-up.** .NET first runs unoptimized code
  and switches to optimized code only after a method has run many times.
  With 3 passes after 1 warm-up its fastest pass varied from run to run
  by up to 4.9x (HBO-WLC 99.6 ms on 2026-11-15 vs 20.2 ms warmed up), so
  it got 20 passes after 3 warm-ups; their median is within 2% of the
  fastest. usfm-grammar (Node) was also given warm-up passes, but its
  figures changed by less than 10%.
- **usfmtc 0.4.8 and 0.4.10 run at the same speed** (within 3%, either
  way, measured side by side), so only the current release is shown.
- **usfm_tools 0.1.1** (Rust, github.com/mimbrown/usfm) includes the
  semantic checks that `usfm_tools::parse` always runs (1.5-12% of its
  time).
- **libusfm's figures include freeing the tree.** Timing parse only gives
  the same numbers within noise: freeing an AST is five `free` calls.
- **Decoding is excluded for every parser.** Each harness reads and
  decodes the files before timing; libusfm does no UTF-8 validation in
  this release.
