# libusfm 0.1.1

A speed-only release: the scanner finds text and attribute boundaries
64 bytes at a time with SIMD. The public API, the AST and every parse
result are unchanged.

## What changed

- A new internal block classifier, with SSE2, AVX2, AVX-512BW, NEON and
  wasm simd128 versions. The version is chosen at compile time (see the
  SIMD comment in `usfm.h`); there is no runtime CPU detection. A plain
  x86-64 build gets SSE2; build with `-mavx2` or `-march=native` for AVX2.
- The scanner caches the masks of its current 64-byte block, so one
  classification serves every token in that block.
- A new configuration macro, `USFM_SIMD_NONE`, forces the v0.1 byte loops.
- Nothing is read past the end of the input on any path. A partial last
  block is classified from a zero-padded copy.

## Verification

- The block scanner and the v0.1 byte-loop scanner are compared token by
  token: in the unit tests (crafted inputs around every 64-byte boundary,
  every input length up to 512 bytes, 20,000 random inputs), over every
  bundled corpus, and on every fuzz input. Every SIMD classifier is
  compared against a scalar reference, including on every 64-byte block
  of every corpus.
- The bundled corpora are WEB-STRONGS (the World English Bible with a
  Strong's tag on every word, the only corpus before this release), WEB
  (the same text untagged), HBO-WLC (Hebrew), CMN-CUV (Chinese), ARB-VD
  (Arabic) and GRC-BYZ (Greek); all of them are run on every SIMD path
  and each gives an identical AST checksum on scalar, SSE2 and AVX2
  (native), NEON (`qemu-aarch64`) and wasm simd128 (`zig cc`, Node
  WASI). See `tests/corpus/README.md`.
- AVX-512BW compiles cleanly but has not been run yet. It needs Intel SDE
  (`USFM_SDE=/path/to/sde64 ./build.sh test-avx512`) or AVX-512 hardware.
- Six local Paratext projects (448 books) also gave identical tokens on
  SSE2 and AVX2.
- A 30-minute libFuzzer run on the AVX2 build found nothing: 7.57M inputs,
  each also checked by the two-scanner comparison, with no crashes, leaks,
  timeouts or scanner differences.

## Performance

Whole-corpus parse (parse + free), fastest of 7–9 passes, clang -O3
-march=native, Intel i7-1355U. Each variant differs only in which SIMD
path is compiled in; scalar is the v0.1 scanner.

**P-core (CPU 2)**

| Corpus | Size | scalar (v0.1) | sse2 | avx2 | avx2 vs scalar |
| --- | ---: | ---: | ---: | ---: | ---: |
| WEB-STRONGS | 19.04 MiB | 393 MiB/s (48.4 ms) | 438 MiB/s (43.4 ms) | 456 MiB/s (41.7 ms) | 1.16x |
| HPUX | 5.32 MiB | 576 MiB/s (9.24 ms) | 697 MiB/s (7.63 ms) | 734 MiB/s (7.26 ms) | 1.27x |
| UDI1_large | 3.61 MiB | 563 MiB/s (6.41 ms) | 656 MiB/s (5.50 ms) | 698 MiB/s (5.16 ms) | 1.24x |

Cycles on the P-core, WEB-STRONGS: 221.2M (scalar), 190.9M (sse2), 184.9M (avx2).

**E-core (CPU 6), median of 3 runs**

| Corpus | scalar (v0.1) | sse2 | avx2 | avx2 vs scalar |
| --- | ---: | ---: | ---: | ---: |
| WEB-STRONGS | 229 MiB/s (83.0 ms) | 268 MiB/s (71.1 ms) | 275 MiB/s (69.2 ms) | 1.20x |
| HPUX | 387 MiB/s (13.8 ms) | 452 MiB/s (11.8 ms) | 465 MiB/s (11.4 ms) | 1.20x |
| UDI1_large | 374 MiB/s (9.66 ms) | 428 MiB/s (8.44 ms) | 440 MiB/s (8.20 ms) | 1.18x |

The WEB-STRONGS rows were measured when that corpus was still called
WEB. HPUX and UDI1_large are ordinary Paratext projects (long text
runs); WEB-STRONGS tags every word (`\w …|strong="…"\w*`), so its
tokens are tiny. The scanner is about half of the parse, so these
whole-parse gains come from roughly halving the scanner's cost.
