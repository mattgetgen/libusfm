# libusfm 0.1.1

A speed-only release: the scanner finds text and attribute boundaries
64 bytes at a time with SIMD. The public API, the AST and every parse
result are unchanged.

## What changed

- A new internal block classifier, with SSE2, AVX2, AVX-512BW, NEON and
  wasm simd128 versions. The version is chosen at compile time (see the
  SIMD comment in `usfm.h`); there is no runtime CPU detection. A plain
  x86-64 build gets SSE2; build with `-mavx2` or `-march=native` for AVX2.
- The scanner caches the masks of its current 64-byte block, so one
  classification serves every token in that block.
- A new configuration macro, `USFM_SIMD_NONE`, forces the v0.1 byte loops.
- UTF-8 validation (new in 0.1.0) uses SIMD on SSSE3, AVX2, AVX-512BW,
  NEON and wasm simd128 builds: one Keiser-Lemire pass over the whole
  input, with per-run checks only when it finds invalid bytes. The
  diagnostics are the same on every build.
- Nothing is read past the end of the input on any path. A partial last
  block is classified from a zero-padded copy.

## Verification

- The block scanner and the v0.1 byte-loop scanner are compared token by
  token: in the unit tests (crafted inputs around every 64-byte boundary,
  every input length up to 512 bytes, 20,000 random inputs), over every
  bundled corpus, and on every fuzz input. Every SIMD classifier is
  compared against a scalar reference, including on every 64-byte block
  of every corpus.
- The SIMD UTF-8 validators are compared with the scalar DFA on every
  1-4-byte edge sequence at every chunk-boundary offset, on random and
  encoded strings, and on every corpus file, on all paths including
  NEON (qemu), wasm (Node) and AVX-512BW (SDE).
- The bundled corpora are WEB-STRONGS (the World English Bible with a
  Strong's tag on every word, the only corpus before this release), WEB
  (the same text untagged), HBO-WLC (Hebrew), CMN-CUV (Chinese), ARB-VD
  (Arabic) and GRC-BYZ (Greek); all of them are run on every SIMD path
  and each gives an identical AST checksum on scalar, SSE2 and AVX2
  (native), AVX-512BW (Intel SDE 10.13.1, `-spr`), NEON (`qemu-aarch64`)
  and wasm simd128 (`zig cc`, Node WASI). See `tests/corpus/README.md`.
- AVX-512BW runs under Intel SDE
  (`USFM_SDE=/path/to/sde64 ./build.sh test-avx512`): the unit tests and
  all six corpora pass, with 0 scanner or classifier differences. On
  distributions that set `vm.max_map_count` to a 10-digit value (Pop!_OS
  does), SDE's Pin engine fails to start; lowering it temporarily (for
  example `sudo sysctl -w vm.max_map_count=1048576`) works around that.
- Six local Paratext projects (448 books) also gave identical tokens on
  SSE2 and AVX2.
- A 30-minute libFuzzer run on the AVX2 build found nothing: 7.57M inputs,
  each also checked by the two-scanner comparison, with no crashes, leaks,
  timeouts or scanner differences.

## Performance

Three changes affect speed against 0.1.0:

- **SIMD scanning** of text and attribute runs (SSE2, AVX2, AVX-512BW,
  NEON, wasm simd128).
- **O(1) text-flag upkeep when trimming.** 0.1.0 rescanned a whole text
  node after trimming its trailing newline, to recompute the CR/LF/TAB
  flag. That was a third of all parse instructions on WEB. It now uses
  the first CR/LF/TAB offset the scanner already saw. This helps every
  build, including scalar.
- **SIMD UTF-8 validation.** Validation is on by default since 0.1.0.
  - **SIMD builds** check the whole input in one Keiser–Lemire pass
    instead of checking every text run.
  - **SSE2 needs SSSE3 for it.** A plain x86-64 build has SSE2 but not
    SSSE3, so it still checks per run. Build with `-march=x86-64-v2` (any
    x86-64 CPU from about 2009 on) or newer to get the SSSE3 validator.

Whole-corpus parse (parse + free), fastest of 27 passes, clang -O3, Intel
i7-1355U with the power profile set to "performance", current corpus
snapshots, measured 2026-11-18.

**Where the gains are:**
- **Plain long-text corpora gain the most.** Hebrew and Arabic have almost
  no inline markup.
- **The word-tagged corpora gain least.** WEB-STRONGS and GRC-BYZ tag every
  word with a Strong's number, so their tokens are tiny and most of the
  time goes to building the tree, which this release does not change.
- **What validation costs on AVX2** (against "validation off"): 2-8% on
  the corpora with inline markup, and 16-19% on Hebrew and Arabic. That
  is 0.3-0.5 ms, because their parse is so fast to begin with.
- **The plain SSE2 build** has no SIMD validator, so it is no faster than
  scalar on the word-tagged corpora.

## Compared with other USFM parsers

Each parser parsed every corpus with its own benchmark harness, in one
session on 2026-11-18, on the same machine, with the power profile set to
"performance" and pinned with `taskset -c 0-3`. Figures are the fastest
whole-corpus pass in MiB/s.

| Parser | Timed passes | Warm-up passes |
| --- | ---: | ---: |
| libusfm | 27 | 0 |
| usfm_tools | 5 | 1 |
| usfm3, tree-sitter, the `usfm` crate | 3 | 1 |
| ParatextData | 20 | 3 |
| usfm-grammar | 10 | 3 |
| usfmtc | 2 | 0 |

- **libusfm validates UTF-8 in these figures, the other parsers don't.**
  Each harness reads and decodes the files before timing. For the Rust
  parsers, decoding is where UTF-8 validation happens, so it is not in
  their times. libusfm's figures include its own validation, so the
  comparison is conservative for libusfm.
- **ParatextData needs a long warm-up.** .NET first runs unoptimized code
  and switches to optimized code only after a method has run many times.
  - With 3 passes after 1 warm-up, its fastest pass varied from run to
    run by up to 4.9x (HBO-WLC 99.6 ms on 2026-11-15, against 20.2 ms
    warmed up). So it gets 20 passes after 3 warm-ups, whose median is
    within 2% of the fastest.
  - usfm-grammar (Node) also gets warm-up passes, but they changed its
    figures by less than 10%.
- **usfmtc 0.4.8 and 0.4.10 run at the same speed,** within 3% either
  way, measured side by side. Only the current release is shown.
- **usfm_tools 0.1.1** (Rust, github.com/mimbrown/usfm) includes the
  semantic checks that `usfm_tools::parse` always runs, which take 1.5-12%
  of its time.
- **libusfm's figures include freeing the tree.** Timing the parse alone
  gives the same numbers within noise: freeing an AST is five `free`
  calls.
